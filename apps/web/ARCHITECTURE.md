# Frontend architecture

Authentication and users are backed by the HTTP gateway. `features/auth/` owns the session query and public account flows; `features/employees/` owns HR user queries/mutations. User/account IDs differ from employee/profile IDs; workforce always uses employee IDs. Sessions are recovered through `/api/auth/me`, persisted by HttpOnly cookies, and cleared along with query caches on logout/401. Service failures render retry UI without fabricating a logged-out session.

HR routes are `/dashboard`, `/karyawan`, `/kehadiran`, `/pengajuan`, `/laporan`, and `/settings`. Employee routes are `/employee`, `/employee/histori`, `/employee/pengajuan`, `/employee/profil`. `/account` changes the current password. Public routes are `/login`, `/register`, `/forgot-password`, `/reset-password`, `/activate`. Guards use the backend role; there is no role/employee picker. Employee clients load only their own profile.

Attendance, requests, photos and progress are persisted by the attendance service. HR dashboard and report queries use persisted workforce data. Karyawan and profile data are real database state.

- `features/workforce/` owns the shared attendance/request types, validation, state transitions, GPS boundary, and session hook. `AppRouter` loads the workforce snapshot through the gateway. Employee and HR attendance and requests use employee profile IDs.
- `features/employee-portal/` owns employee pages, the camera workflow, and request creation. HR imports its attendance detail view through the public index. All employee dates and times use Asia/Jakarta (WIB).
- HR configures one work location (initially unset; default radius 100 m) and the WIB check-in time in Settings. `features/workforce/` owns the form and the map picker. The picker uses Leaflet and OpenStreetMap tiles by default; set `VITE_WORK_MAP_TILES_URL` in the web environment before building to use a compatible tile source, with its required attribution. Settings load and save through the HTTP gateway. Both check-in and checkout require a fresh browser location inside the radius and reported accuracy no worse than the radius. Coordinates, accuracy, distance, photo, capture/submission timestamps, and a location snapshot are retained per event.
- The camera uses an oval positioning guide, without automated face detection. Streams stop after capture or on closing/navigating away; late permission grants are cleaned up. Camera/GPS require HTTPS or localhost. The flow supports retakes and location retries without discarding the photo/progress draft. No location is tracked continuously.
- A day has one check-in/out pair. The form rejects submission across a WIB date change, and an incomplete previous day uses an override. Checkout requires a rich text progress report (up to 10,000 text characters). The Tiptap editor loads on demand, stores JSON, and permits paragraphs, bold, italic, and lists; it does not render arbitrary HTML.
- Employee Beranda keeps the last workforce snapshot if a refresh fails, but blocks attendance until the server state is refreshed. A confirmed save is distinct from a successful refresh. A lost or ambiguous submission response requires a status check before another submit.
- Cuti, Sakit, Izin, and Koreksi absensi share typed requests across roles. HR override approval validates the current record version, atomically changes effective times, and appends before/after times, reason, reviewer, and decision time. Original photos/GPS remain unchanged; corrections never fabricate missing evidence. Leave approval changes the request status only, without a leave balance or automatic attendance change.
- `features/reports/` owns HR `/laporan` and its monthly gateway query. The gateway combines attendance totals with employee profiles, and the query cache is refreshed after workforce or employee updates. The report shows recorded check-ins and approved leave through today in WIB. Absence totals await a work calendar.

- `app/` composes the application, router, and providers; `pages/` owns page-level composition.
- The HR dashboard shell uses a desktop sidebar above 900px and a fixed five-tab mobile navigation at or below 900px. Settings is in the desktop sidebar and the mobile header. Mobile pages scroll above the safe-area-aware navigation; route changes reset page scroll and animate only the page content, respecting reduced motion.
- The employee shell uses a centered column up to 640px and four fixed bottom tabs at every viewport. Both roles use the shared mobile navigation and sliding active indicator. The employee route layout keeps the navigation mounted during page changes and snapshot loading. Page content resets scroll on route changes and shares the HR mobile page transition. Mobile camera dialogs fill the viewport. Dialogs trap focus, lock background scrolling, and restore focus on close.
- `features/<name>/` owns business-specific components and data. Other features and pages import only its `index.ts` public API. Add feature-local `api`, `hooks`, types or schemas only when needed.
- `shared/` contains code reused across features. Use `shared/api/http.ts` for requests through `/api` on the HTTP gateway. Vite proxies this path to localhost:3000 in development; production hosting must route `/api` to the gateway and serve `index.html` for frontend routes.
- Use TanStack Query hooks in the owning feature for actual server state, with feature-scoped query keys and invalidation after relevant mutations. Keep transient UI state in React. Do not cache demo constants as server data.
- The HTTP client includes credentials and the custom CSRF header. Mutations use JSON. Feature account operations send a stable Idempotency-Key per form/action for retry. Auth types reflect gateway responses; never read cookies or store credentials/tokens in localStorage.

Run `npm run typecheck -w @dexatrack/web`, `npm run lint -w @dexatrack/web`, `npm run test -w @dexatrack/web`, and `npm run build -w @dexatrack/web`. Tests live next to the code they cover as `*.test.ts(x)`.

Run `npm run test:e2e:attendance -w @dexatrack/web` after building the backend, starting the local Docker dependencies, and installing Playwright Chromium. It uses synthetic camera/GPS, temporary photo storage, and the dedicated `_test` databases, which it clears. Run it separately from backend integration suites.
